# Data Profile: Kaggle Borg 2019 Sample (`borg_traces_data.csv`), secondary dataset

> **Status:** superseded as the primary dataset by the Azure Functions Trace 2019 ([data_profile_azure.md](data_profile_azure.md)). Retained for over-provisioning calibration and rightsizing analysis.

Generated by `ingestion/parse_kaggle.py` + `ingestion/profile_kaggle.py` on the full file. Re-run both scripts to reproduce every number below.

## Summary

The file is a **cross-sectional random sample** of usage records from the Google Borg 2019 trace. It is suitable for rightsizing analysis (requested vs. used resources) and for anomaly-feature work. It is **not suitable for time-series forecasting or for replay as a continuous telemetry stream**: no job, instance, tenant or cluster has a continuous usage history, and even the whole-trace aggregate shows no temporal structure.

### Data-quality notes

- **Event-time sentinels:** `time == 0` on 56,452 rows (event occurred before the trace window), `time == INT64_MAX` on 3 rows (after the trace window). These are Borg conventions, not errors. They are converted to null with flags `time_before_trace` / `time_after_trace`.
- **Usage windows** (`start_time`/`end_time`) are clean: every row has a window of 1–300 s inside the 31-day trace.
- **Nested fields:** `resource_request`, `average_usage`, `maximum_usage`, `random_sample_usage` parse cleanly as Python dict literals. `constraint` and `start_after_collection_ids` are numpy-printed lists (no comma separators) and cannot be parsed with `ast.literal_eval`. Only their element counts are kept.
- **`random_sample_usage.memory`** is null on every row; it is effectively a CPU-only field.
- **CPI/MAPI missingness** (30.7% overall) depends on event type: 58.5% on SCHEDULE, 56.9% on KILL, 42.2% on EVICT, 17–30% on FAIL/ENABLE/FINISH/LOST. Policy: exclude CPI/MAPI from core features; use only as optional anomaly-model features with an explicit `cpi_missing` indicator, never imputed.

## Why this file cannot drive forecasting

| Test | Result | Meaning |
|---|---|---|
| Distinct 5-min windows for any single job | **max 4** of 8,928 possible | No per-job history exists |
| Distinct 5-min windows for any single instance | **max 4** | No per-instance history exists |
| Tenant #1 hourly CPU series | 496 of 744 hours empty; 24 h autocorrelation 0.025 | Per-tenant series is mostly gaps and noise |
| Tenant #10 hourly CPU series | 736 of 744 hours empty | Unusable |
| Whole-trace hourly row count | min 0, median 254, max 9,907 | Bursty sampling, not demand |
| Whole-trace hourly CPU autocorrelation | 1 h: 0.056, 24 h: 0.004, 168 h: −0.025 | No diurnal or weekly pattern, so nothing to forecast |
| Most-repeated instance | 7,704 rows over only 2 windows on 6,640 machines | Join/duplication artefact in the export |

Real cluster workloads show strong diurnal autocorrelation. Its absence here means the export sampled rows independently of time, which destroyed the temporal structure. A forecaster trained on this would not beat a constant-mean baseline, and replaying it would look like random noise rather than telemetry.

## Decision taken

The primary dataset was switched to the Azure Functions Trace 2019, which has continuous per-minute data for 14 days (see [data_profile_azure.md](data_profile_azure.md)). This file is kept for cross-sectional rightsizing analysis: its request-vs-usage ratios calibrate the static over-provisioned baseline.
